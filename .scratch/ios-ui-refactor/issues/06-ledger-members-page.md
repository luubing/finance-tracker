**契约（后续 ticket 直接使用）**

- **假云端**：`FakeCloud().start()` 起在 `127.0.0.1:E2E_CLOUD_PORT`（默认 5271，`server.ps1` 已把 Web.Server 指向它）；`CloudWorld(cloud, db)` 造「云端上的人 / 别人的账本 / 成员关系」（`world.me(phone)`、`world.person()`、`world.foreign_ledger(...)`、`add_member(...)`）；`cloud.fail(method, path_regex, status, message, times=1)` 注入失败；`cloud.stop()` / `cloud.start()` 模拟云端不可用与恢复；`cloud.calls(method, path_regex)` / `cloud.wait_request(...)` 核对云端收到的请求。假云端镜像真实控制器的状态码 / 消息 / 过滤规则，**不是**真实服务。
- **云端失败文案只在一处翻译**：`LedgerMemberPresentation.DescribeFailure(action, ex)`，后续任何调云端的页面（共享、同步、报表分享……）直接复用，不要在页面里散落「xx失败: {ex.Message}」。
- **页面写日志、不把内部细节给用户**：失败提示是翻译过的、不含内部细节的文案；真正的异常由页面 `ILogger` 记到服务端日志（`%TEMP%\ft_webserver.log`），E2E 失败信息里会带上日志里最近的 `warn` / `fail` 条目。
- **云端写操作的页面骨架**：`RunAsync(action, operation, successMessage, reload)`（`_busy` 防重入 → 执行 → 成功 Toast → 刷新；失败 → 日志 + `DescribeFailure` 的 Toast）可以直接照抄。
- **Alert 的目标对象在 `OnClosed` 里清理**，且每个 Alert 用自己的目标变量（操作菜单收起动画结束时只清理菜单自己的目标）；确认 Alert 要放在操作菜单**之后**（同一层级后渲染的盖在上面，菜单收起动画期间 Alert 已经弹出）。

**与 ticket 文字的差异（均已评估）**

1. **转让所有权、移除成员新增了 Alert 确认**：迁移前这两个危险操作点图标就直接执行。ticket 明确要求「危险操作用 Alert 确认」，按 ticket 执行（属于对既有行为的有意加强，不改变服务层规则）。
2. **「修改角色」改成一步切换**：迁移前是对话框里选角色再保存；现在操作菜单直接给出「改为只读成员 / 改为可编辑成员」（成员只有两个可分配角色，选择即确定，少一次弹层）。服务层调用与校验不变。
3. **邀请手机号的格式校验在页面里就地做**：与登录同一套规则（`PhoneValidator`），不发请求、不弹 Toast，错误行直接出现在输入框下并把焦点还给输入框；「是否已注册 / 是否已是成员」只有云端知道，仍由云端判定后走 Toast（ticket 要求 Toast 呈现的错误语义不变）。
4. **成员关系已知时不再用账本归属兜底所有者**（见对照表）：这是转让所有权后「原所有者仍看到管理入口」的修复，不是行为放宽——云端不可用且本地没有成员关系时仍按账本归属兜底。

**实现要点 / 发现**

- **云端的「拉取」只给我的成员行 + 账本里其他人的生效成员行**：已删除的成员行不会下发，所以「所有者移除别人」后必须本地对齐（否则成员页 / 成员数 / 共享状态永远不变）。对齐用软删除并放在 `SyncTimestampScope` 内保存（不盖本机时间）：对方被重新邀请时，云端更晚版本的成员行才能压过本地的删除标记（单测覆盖）。
- **失败提示不带内部细节**：5xx 的响应体（异常类名 / 栈片段之类）一律不出现在界面上；曾因此给页面补了日志，否则排障时看不到真正原因。
- **Toast 会在几秒后消失**，E2E 的「等不到 Toast」类失败往往在超时时已无从复盘：`expect_toast` 现在在触发操作前挂 `MutationObserver` 记录之后出现过的每一条 Toast，失败信息同时带上弹层状态、断线重连状态、假云端最近请求与服务端日志警告。
- **页面被放弃时的 `ObjectDisposedException`**：用户（或 E2E）在成员页首次加载尚未结束时就整页刷新 / 关闭，旧电路的 DbContext 已被释放，加载抛 `ObjectDisposedException`，页面按「加载失败」处理并写一条 `warn` 日志——这是预期的、无害的；服务端日志里看到它不代表出了问题。
- **一次未能复现的偶发失败**（如实记录）：新增本页后的第一次全量 `run_all.py` 中，本脚本 G 段的「转让确认」出现 1 次「没有出现提示、假云端也没收到 POST」，其后同一脚本单独运行 3 次（冷启动 1 次）、专项压力循环（转让 / 退出流程，4 倍降速 + 满载 CPU 干扰进程）24 轮、全量 `run_all.py` 又跑 1 次全部通过；没能在失败现场取得日志。已补上上述诊断与服务端日志，**再出现时按失败信息里的「触发后出现过的 Toast / 页面状态 / 服务端日志警告」定位**。
  - **后续（08 号 ticket 回归中再次出现，取得了日志）**：同一步「转让」失败，服务端日志是 `HttpRequestException ← IOException ← SocketException 10053`（本机软件中止了已建立的连接，发生在读响应首字节），假云端没收到该请求；单独重跑通过。排除了假云端自身（Python 并发压测 3 600 次请求 0 错误）。同时发现 Windows 11 上 `localhost` 先解析到 `::1`、而假云端只监听 IPv4，**每个云端请求白白多 2 s**（`127.0.0.1` ≈ 1 ms），会放大所有时序问题——E2E 的云端地址已统一为 `http://127.0.0.1:5271`（`server.ps1` / `fake_cloud.py` / README）。10053 本身仍未能解释；修复后的全量回归通过、未再复现，但不能证明已根除。另外借提速暴露并修复了本脚本的三处同步竞态（相同文案的 Toast、菜单关闭动画、操作进行中行按钮 `disabled`），见 08 号 ticket。
