## 实现说明

- 覆盖 spec 用户故事：91。
- 设计稿：07 · 逐页改动清单中 `/import` 一行（沿用二级页面模板）。**设计稿没有导入页的专属画面**（screens 的 13 张里没有），视觉按二级页面模板 + 设置式分组列表（`GroupedList` / `ListCell`）+ 「记一笔」的行内选择器手法。
- 导入接口由客户端上报 `UtcOffsetMinutes`，账单时间在库里一律是 UTC，界面不得自行换算时区，遵守 ADR 0005。
- 导入写入云端数据库：所选账本若是刚在本机创建、还没同步上去，云端会找不到它——这是既有行为，本 ticket 不改，但提示文案要说清楚（做法：导入前先尽力同步一次账本；账本确实不在云端时服务端的「账本不存在」原样告诉用户）。
- 术语：「账单」「账本」「数据来源」。

**判断记录（均已评估，评审阶段会再向用户确认）**

1. **~~选完文件自动解析，去掉了「解析预览」按钮~~ → 已恢复显式「解析预览」按钮（第 2 轮评审，用户拍板 `import_button`）**：ticket 的流程是「选文件 → 解析预览」，旧页面也是选完文件再点一下按钮。恢复后的做法：①选好文件只读入、停在「已选文件」（`ImportStage.Ready`，不自动向云端解析）；②解析预览放在**底部固定的主按钮**上——同一个位置按步骤换动作：「解析预览」（没选文件置灰）→「导入 N 条账单」→「继续导入」，用户始终只有一个主按钮要点，不另加页内按钮；③换来源后已读入的文件保留、预览作废、回到「已选文件」，由用户再点「解析预览」（不再自动重新解析）；④失败提示条里的「重试」保留，与底部「解析预览」是同一个动作（`ImportPresentation.CanParse` 同一条规则，连点两下只发一次请求）。
2. **预览明细最多显示 100 行**（汇总与导入针对全部账单，页面写明）：几千条账单一次性渲染会让页面卡顿；旧页面无上限但限高 360px 滚动。**待用户确认**上限（或改成「查看全部」展开）。
3. **没有单独的「取消」按钮**：旧页面的「取消」只是清空预览；新页面里换文件 / 换来源 / 返回都等价于取消，多一个按钮是冗余。**待用户确认**。

**实现要点 / 发现**

1. **旧页面从未带账本，所以账本必填之后它已经导入不了**：`ConfirmImport` 的请求只有 `CsvContent` 与 `UtcOffsetMinutes`，而服务端校验顺序是「CSV 非空 → 偏移范围 → 账本必填（400「请选择要导入到的账本」）→ 账本存在且可写 → 解析入库」。本 ticket 补上账本选择，才让导入重新可用。
2. **E2E 第一次真实运行就抓到一个永远停在「解析中」的缺陷**：选文件的处理函数先把阶段设成 `Parsing`（读取文件也算解析，文件名先显示出来），再调 `ParseAsync`，而 `ParseAsync` 开头有 `if (Busy) return;`——阶段已经是 `Parsing` 即「忙」，于是把自己挡在门外，请求根本没发出。单元测试（纯函数）与读代码都看不出来。修法：`ParseAsync` 不再判断「忙」，由入口各自挡住（换来源在入口处判断；「重试」走 `RetryParseAsync` 带「忙」判断，连点不会发两次请求）。
3. **「等页面落到某个阶段」的 E2E 要防「残留状态」**：页面本来就停在目标阶段时（例如失败后再失败一次、预览后再预览一次），直接等「落到目标阶段」会立刻返回、读到的是上一次的状态，断言随之偶发失败，甚至拿错故障注入（上一次请求还没处理完，下一个 `cloud.fail` 被它消耗掉了）。办法：用 `cloud.delay()` 拖住这一次请求，**先确认进入了中间状态再等结果**；连接被拒绝这类瞬间失败的情形，改按「提示文字与上一条不同」来等。（已写进 `tests/e2e/README.md`。）
4. **假云端的慢请求要睡在锁外**：第一版若在 `_dispatch` 的锁里睡，会卡住同一时刻的其它请求和测试自己读假云端；现在是「锁内记录请求 + 选出该用的延迟 → 锁外睡 → 锁内处理（故障注入、路由）」，请求先记录、到点才响应。
5. **假云端的 CSV 解析是 `CsvParserService` 的镜像**（微信按固定列位置、支付宝按表头名称定位各列），所以它证明的是「页面把文件原样交给云端、把结果原样展示」，不是「真实的账单文件能被正确解析」——后者由 C# 侧的 `CsvParserServiceTests`（真实导出格式的样本）与真机人工验收把关。
6. **支付宝解析器的列布局与真实导出对不上——第 2 轮评审后已修复（用户拍板，实现要点原文保留如下，便于追溯）**。真实导出的列是 `交易时间, 交易分类, 交易对方, 对方账号, 商品说明, 收/支, 金额, 收/付款方式, 交易状态, 交易订单号, 商家订单号, 备注`（字段末尾带制表符、行尾有多余的逗号、表头前有一长段说明），而原先的 `ParseAlipayCsvAsync` 取 `MerchantName = fields[5]`（真实是「收/支」，交易对方在 `[2]`）、`IsIncome = 金额含 "+" 或 fields[3] 含「收入」`（真实的金额不带符号、`[3]` 是对方账号，所以**真实的收入会被记成支出**）、`TransactionId = fields[8]`（真实是「交易状态」，订单号在 `[9]`）。
   **修复**：`ParseAlipayCsvAsync` 先找到含「交易时间 / 交易创建时间」与「金额」的表头行，再用 `AlipayColumns` 按**列名**定位各列（新旧版导出的叫法都认：交易时间 / 交易创建时间 / 付款时间、商品说明 / 商品名称、金额 / 金额（元）、交易订单号 / 交易号；时间、收/支、金额三列缺一个就解析不出）；行内规则：「收/支」必须是收入 / 支出（「不计收支」不计入）、交易状态是交易关闭 / 已关闭 / 已撤销 / 已失效 / 已全额退款 / 失败的行不计入（与微信一致，属于修复之外的小扩展）、金额 > 0、描述取「商品说明 → 交易分类 → 交易对方 → 支付宝交易」、商户取「交易对方 → 交易分类 → 支付宝交易」、支付渠道仍固定为「支付宝」。新增 `CsvParserServiceTests`（18 个用例：真实布局含制表符 / 行尾逗号 / 说明行、旧版布局、列顺序打乱、带 BOM 的表头、缺必需列、各种无效行、占位符回退，另含 1 个微信解析的回归用例）；`fake_cloud.py::parse_alipay_csv` 同步镜像，E2E 的支付宝 fixture（`import_page_test.py` / `e2e_base_test.py`）换成真实的列布局。其余（微信的解析、导入接口、`UtcOffsetMinutes`、导入不去重）不变。
   **第 3 轮评审补充**：按表头定位列之后，微信与支付宝的导出有好几列同名（交易时间 / 金额 / 收/支……），选错来源会把微信账单悄悄导成「支付宝」账单——`AlipayColumns.LooksLikeWeChat`（表头含微信才有的「当前状态」列）时判为不可用，页面显示「未解析出任何账单」；`fake_cloud.py` 同步镜像，单测 `支付宝_把微信账单当支付宝解析_不解析出任何账单`；E2E 里「把微信文件当支付宝」的小节据此一致。
7. **同步账本会推送本机的全部账本（含已软删除的）再拉取**：这是 `SyncService.SyncLedgersAsync` 的既有行为；导入前调用它是安全的（推送是幂等的），但意味着导入前同步可能顺带把别的本地账本改动推上去——与用户手动点「立即同步」等价。
8. **导入不做去重**（既有行为）：同一份文件导入两次会得到两份账单，所以失败提示里才强调「云端可能已经收下」。
9. **Web.Server 下的 `InputFile` 走 SignalR 分片读流**（E2E 实测：文件内容经 `ReceiveJSDataChunk` 回传），MAUI Hybrid 是进程内通道，两者差别归真机验收；10 MB 的文件在 Web.Server 下也能读完（E2E G 节用 10 MB + 1 KB 的文件测上限拦截，没有读它）。
