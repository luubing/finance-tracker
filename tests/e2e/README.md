# E2E 测试（Playwright，手机视口）

针对 FinanceTracker.Web.Server（Blazor Server）的端到端冒烟与回归测试。所有脚本统一经共享基座
`e2e_base.py` 启动：**手机视口 390×844 + 触摸 + 3 倍像素比**，登录、造数据、手势、错误采集、等待都复用同一套 helper。

> E2E 只能覆盖网页层（Web.Server 与 MAUI 共用的 `FinanceTracker.Web`）。原生能力——状态栏图标颜色、安全区注入、
> 触感反馈、真机玻璃性能——无法在这里验证，由各 ticket 的人工验收覆盖。

## 环境准备

```powershell
# 1. 安装依赖
pip install -r tests/e2e/requirements.txt
python -m playwright install chromium

# 2. 启动 PostgreSQL（API 需要时）
docker compose up -d

# 3. 启动 Web.Server（先 build，再以 http 启动配置后台运行，等端口就绪才返回；监听 http://localhost:5999）
powershell tests/e2e/server.ps1 -Action start
```

`server.ps1` 的动作：`start`（默认，加 `-NoBuild` 跳过编译）、`stop`、`restart`、`status`；`-CloudPort`（默认 5271）指定假云端端口，见下。
日志在 `%TEMP%\ft_webserver.log`。**改了 Razor / C# 后要 `restart`**（运行中的进程会锁住 dll，不重启就测不到新代码）；
只改 `wwwroot` 下的 CSS / JS 刷新页面即可。

也可以手动启动：`dotnet run --project server/FinanceTracker.Web.Server --launch-profile http`。
不加 `--launch-profile http` 时，`dotnet run` 使用第一个启动配置（`https://localhost:6001`），脚本会连不上。

脚本默认访问 `http://localhost:5999`。地址不同时设置环境变量覆盖，无需改脚本。

| 环境变量 | 作用 | 默认 |
|---|---|---|
| `E2E_BASE_URL` | Web.Server 地址 | `http://localhost:5999` |
| `E2E_HEADED` | `1` 时有头运行，人工观察 | 无头 |
| `E2E_SCREENSHOTS` | `1` 时 `shot()` 输出 PNG，供人工对照设计稿 | 关闭 |
| `E2E_SCREENSHOT_DIR` | 截图目录 | `tests/e2e/screenshots/`（已 `.gitignore`） |
| `E2E_DB_PATH` | 造数据写入的本地 SQLite | `%LOCALAPPDATA%\finance_tracker.db`（Web.Server 默认库） |
| `E2E_TIMEOUT_MS` | 单次等待超时 | `30000` |
| `E2E_CLOUD_PORT` | 假云端端口（必须与 `server.ps1 -CloudPort` 一致） | `5271` |

### E2E 永远不连真实 Api / 数据库：假云端

Web.Server 登录时会向云端换令牌，成员管理 / 邀请 / 同步都走云端接口（地址 `ApiSettings:BaseUrl`，默认 `http://localhost:5270`，
即开发者本机的真实 Api + PostgreSQL）。为了既不污染真实库、又能覆盖「云端可用」的流程，`server.ps1` 启动 Web.Server 时把
`ApiSettings__BaseUrl` 指向**假云端端口**（`-CloudPort`，默认 5271）——所以 E2E 的随机手机号永远不会写进真实库，
**但环境变量是启动时设置的：改端口后必须 `restart`**。

地址写的是 `http://127.0.0.1:5271`，**不要改回 `localhost`**：假云端只监听 IPv4，而 .NET 解析 `localhost` 时先连 `::1`——
在 Windows 11 上，被拒绝的回环连接（`::1` 和 `127.0.0.1` 一样）要 **2 秒**才返回（08 号实测：监听着的 IPv4 端口，经 `localhost` 每个请求
固定 ≈2.05 s，经 `127.0.0.1` ≈1 ms；端口没人监听时 `localhost` 要 4 s、`127.0.0.1` 要 2 s）。每个云端请求白白多等 2 秒，
读路径给云端的 3 秒期限（`CloudAvailability`）就只剩不到 1 秒余量，全量跑时机器一忙就超时，E2E 因此偶发失败。

- 没有进程监听假云端端口时，云端就是「不可用」（连接被拒绝）——验证降级行为就用这个状态；
- 脚本里 `with FakeCloud() as cloud:` 起一个进程内的内存实现（`fake_cloud.py`，只依赖标准库，只监听本机回环）：登录换令牌 +
  账本成员相关接口（邀请 / 改角色 / 移除 / 转让所有权 / 退出 / 接受或拒绝邀请 / 拉取成员关系），状态码与消息和真实控制器一致，
  拉取的过滤规则也一致；其它接口一律 404 并记入 `cloud.requests`，`cloud.calls(method, path_regex)` 可以断言「没有意外的请求」；
- 页面先读本地缓存，所以本地库必须与云端状态一致——用 `CloudWorld(cloud, db)` 同时写两边（成员行 / 账本 / 「别人」的用户 Id 两边相同，
  登录用户本地 Id 与云端 Id 各自独立，复现生产里的 Id 映射）：`me(phone)` / `person()` / `own_ledger(...)` / `add_member(...)` / `foreign_ledger(...)`；
- `cloud.fail(method, path_regex, status=, message=, times=)` 故障注入（下一个匹配的请求直接失败，不碰状态），
  `cloud.wait_request(...)` 等云端收到某个请求，`cloud.stop()` / `cloud.start()` 模拟云端断开与恢复，`cloud.member(id)` / `cloud.ledger(id)` 读云端状态；
- 账单导入（20 号）：微信 / 支付宝的**解析预览与正式导入**接口（解析规则、校验顺序、状态码与消息对照 `ImportController` + `CsvParserService`；正式导入要求账本必填且可写）+ 同步的最小桩
  （账本推送会登记账本、所有者以令牌为准，其余推送 / 拉取返回「没有变化」）。`cloud.imports()` / `cloud.imported_bills()` 看云端收下了什么，
  `cloud.fail_import_rows({2: "分类不存在"})` 让下一次导入的指定序号入库失败；调用 `cloud.use_import_catalog(expense_category_id=, income_category_id=, channel_id=)`
  （用本地库里的预设 Id）之后，拉取账单接口会把导入的账单还给客户端，「导入 → 自动同步一次 → 账单列表看得到」就能端到端验证；
- `cloud.delay(method, path_regex, seconds, times=)`：让下一个匹配的请求慢几秒才处理（请求先记录、睡在锁外，不会卡住别的请求与测试自己读假云端），
  用来观察「解析中 / 导入中」这类转瞬即逝的中间状态。**页面本来就停在目标阶段时（例如失败后再失败一次），直接等「落到目标阶段」会立刻读到上一次的残留状态**——
  先用 `delay` 拖住这一次请求、确认进入了中间状态，再等结果（`import_page_test.py` 的 `wait_reparsed`）；连接被拒绝这类瞬间失败的情形，改按「提示文字与上一条不同」来等；
- 假云端**不是**真实实现：它保证的是「客户端按真实协议发请求、按真实协议处理响应」；真实服务层的规则由 `dotnet test`
  里接真实云端服务的 `HttpLedgerMemberServiceTests` 等覆盖，与真实 Api + PostgreSQL 的联调仍在集成环境做；
- Web.Server 的 `CloudAvailability` 在读路径联网失败后会记住「云端不可用」30 秒（页面加载时跳过联网刷新、只读本地缓存）；
  **用户主动操作（邀请 / 移除 / 接受邀请…）不受影响，操作成功后记忆被清除**。所以造数据要让本地与云端一致，不要依赖「页面加载时一定会联网刷新」。

### 自动识别的假实现：`/__e2e/capture`

浏览器里没有「通知使用权」，也读不到短信：Web.Server 的默认实现永远是「都没开启、没有短信」，待确认账单页的「均已开启」状态条、授权流程与短信识别页的读取流程就无从验收。
`server.ps1` 启动时设置 `E2E__FakeCapture=true`（配置键 `E2E:FakeCapture`；不设置时行为与平时完全一致，下面的端点也不存在；这些端点没有认证，所以**只在开发环境（Development）生效**——`server.ps1` 用 `--launch-profile http` 启动，环境就是 Development），Web.Server 把 `ISmsService` / `INotificationListenerPermissionService` 换成进程内的假实现
（`server/FinanceTracker.Web.Server/E2ECapture.cs`，MAUI 应用不引用它）：

- `set_capture(reset=, notification=, sms=, sms_grantable=, messages=[{id, address, body, date}])`（`POST /__e2e/capture`）设置通知使用权 / 短信读取权限是否已开启、系统弹窗里用户点的是「允许」还是「拒绝」（`sms_grantable`）、
  「读到的」短信（`date` 是设备本地时间；读取时按开始日期过滤、新的在前）；`capture_state()`（`GET`）返回当前状态与**被调用的次数**
  （`notificationSettingsOpened` / `smsPermissionRequests` / `smsReads` / `lastSmsReadFrom`）——断言「点了『去开启』真的走到了平台服务」靠它；
- 状态是**整个进程共享**的（脚本串行执行）：用到它的脚本开始前与结束后各 `set_capture(reset=True)` 一次，免得互相影响；
- 它只替换原生能力。捕获到一笔支付之后「待确认账单怎么入库、怎么入账」仍走真实的 `PendingBillService` / `BillService`——E2E 用 `seed_pending_bill` 造待确认账单。

### 渲染档位的假实现：`/__e2e/rendering`

真机上「该不该把毛玻璃降级成不透明实色」由原生宿主判定（Android 低内存 / 内存 < 3 GiB 的设备、iOS 系统「降低透明度」），浏览器里没有这个信号，
「宿主判定 → `UiRuntime` → `<html data-ft-solid>` → 设计令牌」这条链路就无从验收。`server.ps1` 启动时设置的 `E2E__FakeCapture=true` 同时把 `IRenderingProfileService` 换成进程内的假实现
（`server/FinanceTracker.Web.Server/E2ERendering.cs`，MAUI 应用不引用它；不设置时行为与平时完全一致，端点也不存在）：

- `set_rendering(True | False)`（`POST /__e2e/rendering`，`{"solid": true}`）设置「宿主偏好实色」，页面里已经打开的 `UiRuntime` 即时跟随（不用刷新）；`rendering_state()`（`GET`）读取当前值；
- 状态是**整个进程共享**的（脚本串行执行）：用到它的脚本开始前与结束后各 `set_rendering(False)` 一次，免得互相影响。

### 错误日志的专用目录：`/__e2e/log-directory`

错误日志页读的是 Serilog 写在本机的日志文件（`app-yyyyMMdd.log`，每行一条 CompactJson），而 Web.Server 自己不写文件日志，E2E 得自己往目录里写日志行来造数据；
「清除日志」又会删掉目录里所有 `app-*.log`——所以 E2E **绝不能碰开发机上真实的日志目录**。`server.ps1` 启动时设置 `E2E__LogDirectory`（配置键 `E2E:LogDirectory`，值是 `%TEMP%\ft_e2e_logs`；
不设置时行为与平时完全一致，下面的端点也不存在；与 `/__e2e/capture` 一样**只在开发环境生效**，生产环境误带该变量也不会改动日志目录），Web.Server 的 `ILogViewerService` 改读这个专用目录（`server/FinanceTracker.Web.Server/E2ELogs.cs`，MAUI 应用不引用它，传的是真实的 `AppDataDirectory/Logs`）：

- `GET /__e2e/log-directory` 返回日志页正在读的目录（`{"directory": "…"}`）；`e2e_base.log_directory()` 取它——取不到说明 Web.Server 不是由 `server.ps1` 启动的，脚本给出指引并以退出码 2 结束（同时保证清除日志的用例不会打到真实目录）；
- `LogFiles`（`e2e_base.py`）按应用真实的文件格式造数据：`write(entries, extra_lines=)` 先清空 `app-*.log`，再按本地日期写成 `app-yyyyMMdd.log`；`log_entry(when, template, level=, source=, exception=, properties=)` 造一条
  （`when` 是本机本地时间，落盘时换成 UTC，`@mt` 里的 `{名字}` 由 `properties` 代入，与 `CompactJsonFormatter` 一致：只有不是 Information 才写 `@l`）；`extra_lines` 往某天的文件里原样追加行（造损坏行）；`files()` / `clear()`。
  **只动目录里的 `app-*.log`**，目录里别的文件不会被清掉（验证「清除只删日志文件」时特意放了一个别的文件）；
- 目录是**整个进程共享**的（脚本串行执行）：用到它的脚本结束时 `clear()`（`log_viewer_page_test.py` 在 `finally` 里清）；
- 页面里读到的时间戳按**机器本地时区**解析（`LogViewerService` 沿用旧实现，分组的「今天 / 昨天」也按本机日期），所以 `log_entry` 的 `when` 与断言里的「今天」都用本机日期，不经过 `AppTimeZone`。

## 运行

```powershell
python tests/e2e/run_all.py                  # 全部（先跑不依赖服务的基座自测）
python tests/e2e/run_all.py login smoke      # 只跑文件名含这些关键字的脚本
python tests/e2e/run_all.py --list           # 只列出会运行的脚本
python tests/e2e/login_addbill_test.py       # 单个脚本
```

退出码：`0` 全部通过；`1` 有失败；`2` 环境未就绪（Web.Server 没启动）。可用于 CI。

`run_all.py` 给每个脚本 30 分钟的上限（最长的 `a11y_degradation_test.py` 约 5 分钟）：超时的脚本被终止，汇总里记 `TIMEOUT`、按失败处理（浏览器进程可能残留，必要时手动结束）。
脚本里 `run.skip(...)` 跳过的检查（环境不具备条件，例如 CDN 图标字体 / ECharts 没加载出来、现在还没到本月 1 日 00:30）不算通过也不算失败，但每个脚本收尾时会在「N/M 通过」下面另起一行列出——看到「全绿」时别忘了看有没有这一行。

### 造数据的约束（直接写库只用于造数，但值必须遵守业务约定）

- **时间口径**：`Bill.TransactionTime` 落库一律是 **UTC**（ADR 0005）。`when` 传入的是本地时间（naive），`to_db_time` 换算成 UTC 文本。
- **同步状态**：新造账单默认「待同步」（`SyncStatus = 0`），不会污染后续对同步状态的断言；需要其它状态用 `set_bill_sync_status`。
- **归属**：账单属于当前登录用户的**本地 Id**（`create_bill` 内部按手机号取库内 Id）；Guid 一律大写，与 EF Core 的 SQLite 存储一致，否则 `=` 比较会失配。
- **账本**：`ledger=None` 写入「历史上没有账本的账单」（`LedgerId = NULL`，统计中归入「未归属账本」）。新建账单在业务上必须有账本，只有为了覆盖历史数据才这样造。
- **待确认账单**：`seed_pending_bill` 写入 `PendingBills`。Web.Server 从 07 号起注册真实的 SQLite 实现（`PendingBillService`，经 `AddDbContextFactory` 每次调用新建上下文），页面读得到库里的待确认账单（首页的横幅与角标、待确认账单页的卡片）；但 Web 端没有通知 / 短信能力，**自动捕获**本身只能由造数据模拟（权限状态与短信读取另见「自动识别的假实现」）。`PendingBills` 不区分用户、所有用例共享一张表：用到它的用例开始前与结束后各调一次 `delete_pending_bills()`，免得互相影响首页的横幅 / 角标；`seed_pending_bill` 写完后页面不会自动感知（没有应用内事件），整页重新进入页面即可。
  **`PendingBills` 的时间列是设备本地的墙上时间，不是 UTC**（通知 / 短信捕获时取的就是 `LocalDateTime` / `DateTime.Now`，页面按墙上时间原样显示，入账时才经 `AppTimeZone` 换成账单的 UTC）：`seed_pending_bill(when=…)` 用 `to_wall_time` 原样写入，不要对它用 `to_db_time`；这与 `Bills.TransactionTime`（一律 UTC）正好相反。
  **`PendingBills.Amount` 是文本，写法要和应用一致**：Microsoft.Data.Sqlite 把 decimal 存成 `"0.0###…"`（至少一位小数、去掉多余尾零：`7` → `"7.0"`、`8.50` → `"8.5"`），应用去重 / 查询按金额做 `=` 比较比的就是这段文本，`"7"` 与 `"7.0"` 不相等——`seed_pending_bill` 已用 `to_db_decimal` 按这个写法存（单元测试 `PendingBillDeduplicationTests` 锁住这个假设）；自己往别的需要「与应用写入对得上」的 decimal 列直接塞值时同样要用它。
- **预算**：`seed_budget(user_id, amount=, category_name=None, ledger_id=None, year=None, month=None)`：`category_name=None` 是总预算，否则是该预设支出分类（用 `category_id_by_name` 取 Id）的预算；`ledger_id=None` 是「全部账本」预算（统计所有支出账单，含历史无账本账单）；年月缺省为本月。

### 稳定签名约定

`create_ledger` / `create_bill` 的签名保持稳定。哪个 ticket 改了对应界面，就由哪个 ticket 同步修改 helper 的内部实现
（05 已把造账本改走新界面；15 把造账单改走新界面——`create_bill` 多了可选的 `page`，传了就经记一笔 Sheet，不传仍直接写库，原有调用不受影响），其余用例不受影响。

## 数据不隔离的约定

Web.Server 与本机共用同一个 SQLite（`%LOCALAPPDATA%\finance_tracker.db`），测试数据**不隔离、不清理**。因此：

- 每个用例用 `login()` 注册一个全新手机号，数据落在这个新用户名下；
- 账本 / 备注一律用 `unique_name("前缀")` 生成带时间戳的唯一名称；
- **只断言自己创建的数据**，不断言全局数量、总金额，也不依赖「库里恰好没有别的数据」。

## 已知限制

- 旧界面的 MASA 下拉（`MSelect`）在无头浏览器里难以自动化选择。基座不为它写补丁，后续 ticket 会用更易自动化的自定义选择器取代它：
  15 号已经把记一笔换成了自定义菜单 / 键盘 / 分类网格（`create_bill(page=…)` 经界面造账单），18 号把预算页换成了自定义 Sheet / 键盘，19 号把待确认账单与短信识别页换成了自定义菜单 / 键盘，20 号把导入页换成了文件行 + 账本菜单，21 号把自定义报表换成了日期输入行 + 账本菜单，22 号把登录页换成了原生手机号输入框、错误日志页换成了搜索框 + 筛选 Sheet——
  至此页面里已经没有 MASA 输入控件 / 下拉（没有调用方的旧 `LedgerSelect` 已在 24 号删除；MASA 只剩 `MApp` / `MErrorHandler`、页面栈、`MECharts` 图表容器），E2E 不再需要为 MASA 控件打补丁。
- 语音识别：无头浏览器没有麦克风与语音服务，E2E 用注入的**假 `SpeechRecognition`**（`voice_overlay_test.py`）驱动真实的前端 / 服务 / 覆盖层链路，只能覆盖「点按」形态（浏览器 Web Speech）；
  MAUI 原生的「按住说话」在 Blazor Server 宿主里不存在（`NoOpSpeechService`），按住 / 上滑取消 / 滑开取消 / 权限弹窗、真实识别服务的网络环境归真机人工验收（ticket 17）。
- 云端相关能力（共享账本邀请的接受 / 拒绝、成员管理）用**假云端**（`fake_cloud.py`）做端到端验证，见上文「假云端」；
  它只实现了成员相关接口、账单导入的预览 / 导入与同步的最小桩，且不是真实的 Api + PostgreSQL：同步（账单 / 分类等的完整推拉）、真实服务层规则、与真实库的联调不在这里覆盖
  （前者的协议由 `dotnet test` 里接真实云端服务的测试覆盖，后者留给集成环境的人工验收）。
- 导入账单（20 号）：假云端的 CSV 解析是 `CsvParserService` 的**镜像**（微信按固定列位置、支付宝按表头名称定位各列；规则以 C# 为准，C# 侧另有 `CsvParserServiceTests` 用真实导出格式的样本把关），
  所以真实的微信 / 支付宝导出文件（编码、表头前的说明行、字段末尾的制表符与行尾多余的逗号）不在这里覆盖，归人工验收。
  支付宝的解析器在第 2 轮评审后改为按表头名称定位列（原先按固定位置取列，与真实导出的列布局对不上，真实的收入会被记成支出），E2E 的支付宝 fixture 已换成真实的列布局；
  它仍然只能证明「页面把文件原样交给云端、把云端的结果原样展示」。文件选择走的是 Web.Server 下真实的 Blazor `InputFile`（SignalR 分片读流），
  MAUI Blazor Hybrid（WebView 进程内通道）与系统文件选择器（`accept=".csv"` 在 Android WebView 里是否生效）的差别归真机验收。
- 自定义报表（21 号）：导出走 Blob + `<a download>`，E2E 能验证下载事件的文件名与内容（含 BOM / 转义 / 不带千分位），但 **MAUI Blazor Hybrid 的 WebView 里这种下载是否真的存盘、存到哪里**不在这里覆盖（Android WebView 需要 `DownloadListener`，iOS WKWebView 对 blob 下载支持有限；若真机不支持，要补原生的保存 / 分享文件通道）；
  分享摘要用 `navigator.share`（系统分享面板）→ 剪贴板，E2E 只能桩住这两个接口验证分支与结果；系统日期选择器（iOS 滚轮 / Android 日历）的手感与可用性同样归真机人工验收。
- 网页里整页进入一个会立刻 `Pop` 的页面（例如非法账本 Id 的成员页）时，`Pop` 是浏览器回退（整页重载），页面里的 Toast 随旧文档消失，
  E2E 只能断言「回到了上一页」；站内（MAUI 里的真实路径）Toast 会保留，归人工验收。
- 退出登录时，`MainLayout`（页面栈 + Tab 栏）换成 `AuthLayout`（登录页）：确认后排入队列的「已退出登录」Toast 随旧布局一起被丢掉（旧「我的」页就是这样）。
  E2E 用 `MutationObserver` 断言「Toast 已入队」，用户是否真的看到它要人工验收；22 号没有在登录页加一次性提示（spec 不要求，认证行为也不变），是否需要列为评审阶段向用户确认的判断项。
- 页面栈（PageStack）只响应它自己发起的导航：脚本里 `Blazor.navigateTo('/xxx')` 只会改地址栏、压不进页面栈，也就没法 E2E「应用内压栈某个旧地址」这类路径；
  能用的做法是点页面里真实的入口，或整页重新进入（`open_app`）。
- Web.Server 的 Blazor 输入框用 `@oninput` + `value` 回写：**每个按键都会往返一次服务端**，Playwright 的 `press_sequentially` 间隔过短（≈ 5 ms）
  会丢字符。键盘输入用接近真人的间隔（≥ 40 ms），或直接 `fill`（一次 input 事件）。
  登录页的手机号框与搜索框是**不受控**的（不回写 `value`，22 号起登录页也改成这样，原因是敲得快时回写会用往返之前的旧值盖掉后来敲的字），不受这条影响。
  另外：**Playwright 的 `fill()` 会被 `maxlength` 截断**（它不是「写入后再校验」），验证「超长输入」时用 ≤ `maxlength` 的数据，或真实按键。
- CDP 合成触摸与真机的差别：见上表「手势」一行关于惯性滑动后第一次 `tap` 的说明；键盘弹出 / 软键盘避让、真机玻璃模糊与帧率、
  左滑跟手的手感在 Web 层都无法验证，归各 ticket 的人工验收。
- 通知栏 / 短信的**真实捕获链路**（`NotificationListenerService` 收到微信 / 支付宝通知、短信广播收到银行扣款短信、写入待确认列表、系统权限弹窗与「通知使用权」设置页往返、回到应用后权限状态重新读取）
  只在 Android 原生存在：E2E 经 `/__e2e/capture` 假实现验证页面对「权限状态 / 读到的短信 / 平台服务被调用」的反应，捕获本身与系统设置页往返归真机人工验收（ticket 19）。
- MASA 提示条（Toast）在**鼠标悬停时暂停消失倒计时**：Playwright 的鼠标停在上一次点击处，而点底部菜单项（ActionSheet）的位置正好在提示条下面，提示条会一直留着、`wait_toasts_gone` 超时。
  真机是触摸、没有悬停，这只是测试环境的现象——等提示条消失之前先 `page.mouse.move(1, 1)` 把鼠标挪开。
- 脚本直接运行 exe（而非 `dotnet run`）时需设置 `$env:ASPNETCORE_ENVIRONMENT='Development'`，否则静态资源不生效。
- Web.Server 加载 MDI 图标字体与 ECharts 走 CDN（`boot.js` 在页面 load 之后注入，不挡首屏）；离线环境下图标不显示、图表位置给「图表组件未能加载」的说明（`EChartsView`），错误采集默认忽略这类加载失败。
- 冷启动的原生部分（`splash.svg` 生成的系统启动画面：Android 12+ SplashScreen / iOS 启动图、应用图标、初始状态栏图标颜色、「启动画面 → 加载页首帧」的衔接）只存在于真机 / 模拟器：E2E 只覆盖加载页之后的 Web 层。
  颜色与尺寸的一致性（令牌 `--ft-splash-bg` / `--ft-splash-tile` ↔ csproj 的 `Color` / `BaseSize` ↔ `MainPage.xaml` 的底色 ↔ `splash.svg` 的方块色）由 `DesignTokensTests` 锁定，真机观感与时序归人工验收；
  加载页的转圈门槛 600 ms / 交接上限 1500 ms / 看门狗 12 s 是建议值而不是实测数据，真机上量过「点图标 → 外壳就绪」的分布之后再调。

- 无障碍与降级（23 号）只有 Web 层被自动扫描：「字号放大」是样式改写的近似，**不等价真实的 Android `fontScale` / iOS Dynamic Type**；
  低端设备判据（系统低内存标记或总内存 < 3 GiB）、降级后的真实流畅度、iOS「降低透明度」「减弱动态效果」的即时跟随、Android 系统「移除动画」是否映射成 `prefers-reduced-motion`、
  强光 / 低亮度下的可读性归真机人工验收（ticket 23）。读屏（VoiceOver / TalkBack）适配审计、Sheet / 语音覆盖层升起时底下页面的 `inert` 与焦点陷阱、Android 返回键先收起 Sheet 都**不在这里覆盖**。
