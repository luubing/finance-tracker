# 共享账本权限模型

## 决策

共享账本采用"单一所有者 + 邀请成员"模型，权限集中在云端（FinanceTracker.Api 数据库），
客户端仅缓存成员关系用于本地账单可见性判定。

## 角色

| 角色 | 权限 |
|------|------|
| Owner | 账本全部权限：管理成员（邀请/移除/改角色）、转让所有权、删除账本、记账与编辑账本内账单 |
| Editor | 记账（账单归属该账本）、查看账本内全部成员账单、编辑/删除自己的账单 |
| Viewer | 只读：查看账本内全部成员账单，不能记账、不能修改任何账单 |

## 邀请与确认

- Owner 按手机号邀请（被邀请人必须已注册，本应用以手机号为唯一标识），
  生成 `LedgerMember` 记录，状态为 Pending。
- 被邀请人在"账本管理"页看到待处理邀请，确认后状态变为 Active（生效），拒绝则记录作废。
- 同一 (账本, 用户) 唯一：曾拒绝/被移除的成员可被重新邀请（复用原记录）。

## 数据可见性

- 账单通过 `LedgerId` 归属共享账本，创建者的 `UserId` 保留。
- 云端拉取端点（bills/ledgers）对 Active 成员开放共享范围内的数据；
  客户端合并到本地 SQLite 时保留原作者 UserId 并标记为已同步（不会被回推，
  推送队列只取 `UserId == 本地用户` 的 Pending 账单）。
- 本地合并时为外部用户创建"用户存根"（仅 Id + 手机号，满足账单/账本外键约束）。
- 统计/预算等按 `UserId` 过滤的功能暂不纳入共享账本内他人账单（保持个人口径）。

## 边界情况

- Owner 不能退出账本，必须先转让所有权（转让后原 Owner 降为 Editor）。
- 成员被移除或退出后，其本地账单副本保留（本地数据），但云端不再向其下发共享账本数据。
- 账本被 Owner 删除（软删除）后，成员端通过既有账本同步感知（IsDeleted 标记随拉取传播），
  不做额外推送通知。

## 考虑的替代方案

- 完全去中心化的成员管理（客户端各自维护成员列表）：无法保证一致性，放弃。
- 细粒度权限（如按分类授权）：记账场景不需要，保持三角色简单模型。
